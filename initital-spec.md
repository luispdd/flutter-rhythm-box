# Rhythm Box — Initial Specification (v1 / POC)

Personal-use proof of concept: a metronome and a step sequencer (simple drum machine) used while practicing guitar or keyboards. All sounds are synthesized; there are no audio sample files.

Read this whole document before writing code. Where this spec is silent or ambiguous, choose the simplest option, record the decision in the relevant OpenSpec change's `design.md`, and continue.

This document is source material for OpenSpec: use it to create the project's specs and changes (one change per milestone in section 9), following OpenSpec's default file conventions. It is not meant to replace those files. Do not silently deviate from anything marked **MUST**.

---

## 1. Goals and non-goals

### Goals
- Rock-solid, consistent rhythm timing. Consistency matters more than raw latency.
- A metronome with an adjustable synthesized click.
- An 8-track step sequencer with 4–16 steps, playing in a loop, with patterns that can be saved and deleted.
- Everything works offline, on-device, no accounts.

### Non-goals (v1)
- Live finger drumming or any input whose latency must be low.
- Pre-recorded samples or importing user samples.
- Swing, velocity, per-step probability, effects, MIDI, audio/MIDI export.
- Chaining patterns into songs (planned for v2, see section 11).
- Voice/rhythm recognition (maybe never).
- Web version (nice to have only; do not design around it).
- Cloud sync.

## 2. Platforms (priority order)
1. **Android** (primary). Test on a real device, not only an emulator.
2. **Linux desktop** (secondary).
3. Web: not a target.

## 3. Technology
- **Flutter** (Dart) for UI and app logic.
- **`flutter_soloud`** (native low-latency audio engine) for playback. Check its current documentation and API before starting.
- Audio is generated by a Dart synth renderer (section 6) and played by the engine.
- If the timing spike (section 8) fails its acceptance criteria, **stop and report the measured numbers** instead of working around it. The planned fallback is a small native audio engine (Rust/Oboe) behind the same interface, but do not build it unless asked.

## 4. Core timing principle (MUST)

**No Dart timer, `Future.delayed`, `Timer.periodic`, or UI-thread scheduler may decide when a sound starts.** Rhythm timing must come from the audio side.

Chosen strategy: **render-ahead, gapless loop.**
- The app renders one full loop (one bar of the metronome, or one full pattern of the sequencer) into a single mono PCM buffer.
- The engine plays that buffer in a gapless loop, so the timing is correct by construction.
- Whenever tempo, step count, time signature, or pattern content changes, the app re-renders the buffer and swaps it in **at the next loop boundary** (not mid-loop, no audible glitch).
- Stopping can happen immediately.

The exact mechanism for gapless looping and boundary swapping (looping a handle, a buffer stream, scheduled playback, etc.) is for you to determine in the spike. Document what you chose and why in the spike change's `design.md`.

### Buffer length
- Sample rate: 44100 Hz, mono, 16-bit PCM (or float, if the engine prefers).
- For the sequencer, a step is a **16th note** (assumption, keep it a single constant `stepsPerBeat = 4`). Samples per step = `sampleRate * 60 / bpm / stepsPerBeat`. This can be fractional.
- Place each step's onset at `round(i * samplesPerStep)` and make the total loop length `round(stepCount * samplesPerStep)`, so rounding errors never accumulate across loops.
- For the metronome, one loop = one bar = `beatsPerBar` beats of `sampleRate * 60 / bpm` samples each (same rounding rule).

## 5. Features

### 5.1 Shared tempo
- One global tempo value (BPM), range **30–300**, default **120**, shared by the metronome and the sequencer.
- Controls: numeric entry, +/- buttons, slider, and **tap tempo** (tap tempo is optional / should-have; do it if it is cheap).
- Changing tempo while playing re-renders and swaps at the next loop boundary.

### 5.2 Metronome (MUST)
- Own **Play/Stop** button, independent from the sequencer's.
- Beats per bar: selectable **2–9** (default 4). The BPM value is beats per minute; the denominator is not modeled in v1 (assumption).
- Accent on beat 1 (toggle, default on): beat 1 plays at a higher pitch.
- Visual beat indicator showing the current beat. Since the visual cannot be driven by a timer, derive it from the audio engine's playback position if available, otherwise from a UI-side estimate that is clearly marked as approximate and never affects audio.
- **Adjustable synth click sound** (no samples):
  - Waveform: sine, triangle, square.
  - Pitch (Hz): e.g. 200–4000, default 1000.
  - Decay length (ms): e.g. 10–200, default 40.
  - Accent pitch: default 1.5 × pitch.
  - Settings are remembered between app runs (simple local settings storage).

### 5.3 Sequencer (MUST)
- Own **Play/Stop** button, independent from the metronome's.
- **8 tracks**, step count adjustable from **4 to 16** (default 16). No swing.
- Step grid UI: tap a cell to toggle it on/off. Tracks ordered with the lowest-pitched voice at the bottom (or clearly labeled), like a classic drum machine.
- Plays in a loop by default (looping is always on in v1).
- Editing steps while playing re-renders and swaps at the next loop boundary.
- When the step count is reduced and increased again, previously entered steps are preserved (store 16 steps per track always; use the first `stepCount`).
- Voices are **automatically generated, not user-configurable** in v1 (see section 6).
- Clear-pattern action.

### 5.4 Patterns: save / load / delete (MUST)
- Save the current sequencer state as a named pattern. A saved pattern remembers: **tempo, step count, and step data for all 8 tracks**.
- List saved patterns, load one (this also sets the global tempo), rename, delete (with a confirmation).
- Storage: local only. One JSON file per pattern in the app documents directory is fine (or any equally simple local store).

### 5.5 Persistence (should-have)
- Last-used tempo, metronome settings, and the sequencer's working pattern are restored on startup.

## 6. Synthesized voices

All sounds are generated by the renderer; each is described by a small parameter set so that future versions can expose editing without changing the model.

```json
{
  "waveform": "sine | triangle | square | noise",
  "startFreqHz": 150,
  "endFreqHz": 45,
  "decayMs": 260,
  "gain": 0.8,
  "highpassHz": null,
  "lowpassHz": null
}
```

- Frequency sweeps from `startFreqHz` to `endFreqHz` over the voice length (exponential is fine). For `noise`, frequencies are ignored and the optional filters shape it.
- Envelope: very short attack (~1–2 ms, to avoid clicks) and exponential decay over `decayMs`.
- When voices overlap in the mix, apply per-voice gain and a soft limiter (e.g. `tanh`) so the sum never clips harshly.

### Default 8-voice ladder (track 0 = lowest, track 7 = highest)
Starting values, to be tuned by ear later. Keep them in one place in code.

| Track | Waveform | Start Hz | End Hz | Decay ms | Notes |
|---|---|---|---|---|---|
| 0 | sine | 150 | 45 | 260 | kick-like |
| 1 | sine | 120 | 70 | 200 | low tom-like |
| 2 | triangle | 180 | 120 | 160 | |
| 3 | triangle | 260 | 200 | 140 | |
| 4 | square | 400 | 400 | 90 | lower gain |
| 5 | square | 800 | 800 | 70 | lower gain |
| 6 | noise | – | – | 80 | highpass ~3000 Hz, snare/hat-like |
| 7 | noise | – | – | 40 | highpass ~7000 Hz, hat-like |

## 7. Architecture

Keep these layers separate (the UI must never contain audio logic):

1. **Domain models** (pure Dart, no Flutter imports): `Voice`, `Pattern`, `MetronomeSettings`, tempo. JSON serialization.
2. **Synth renderer** (pure Dart): turns a voice, or a pattern plus tempo, into a PCM buffer. Fully unit-testable without any audio device.
3. **Audio engine interface**: a small abstract class (e.g. `AudioEngine` with `startLoop(buffer)`, `swapLoopAtBoundary(buffer)`, `stop()`, and a position stream if available) and a `flutter_soloud` implementation. This is the seam that would let a native Rust engine replace it later.
4. **Persistence**: pattern store and settings store.
5. **UI**: two main screens or tabs (Metronome, Sequencer) and a patterns list/dialog. State management: any simple, mainstream choice (e.g. Riverpod or Provider); record the choice.

Suggested repository layout: `lib/domain`, `lib/synth`, `lib/audio`, `lib/storage`, `lib/ui`, plus `test/` and `tools/` (for the timing analysis script).

### Data model (reference)

```json
{
  "id": "uuid",
  "name": "My pattern",
  "tempoBpm": 120,
  "stepCount": 16,
  "tracks": [
    [true, false, false, false, true, false, false, false, true, false, false, false, true, false, false, false],
    "... 8 arrays of 16 booleans in total, index 0 = lowest voice ..."
  ]
}
```

Voices are not stored in patterns in v1 (they are the fixed default ladder).

## 8. Milestone 0 — Timing spike (do this first)

Purpose: prove that this approach is steady enough before building anything else. Build the smallest app that does only this:

- A 4-step sequencer pattern (16th-note steps) at 120 BPM (one hit every 125 ms) looping on a single voice.
- A metronome loop at 120 BPM (one click every 500 ms).
- Swapping to a different tempo/pattern at the loop boundary while playing.

### Measurement (must be automated, not "sounds fine")
- Provide `tools/analyze_timing.py` (or similar) that takes a recording (WAV), detects onsets, and reports inter-onset interval mean, standard deviation, maximum deviation from nominal, and cumulative drift.
- Recording method: record the device's output (loopback/line-in, or an external recorder placed near the speaker) for **5 minutes per test**, on a **real Android device** (speaker or wired headphones; Bluetooth adds large fixed latency and should not be used for this test).
- Also run on Linux desktop.

### Acceptance criteria (targets, report actual numbers)
- Inter-onset interval standard deviation **< 1 ms**.
- Maximum deviation from nominal interval **< 3 ms**, including across loop boundaries.
- Cumulative drift over 5 minutes **< 5 ms**.
- No audible click, gap, or doubled hit when swapping buffers at the loop boundary.

Deliver: the numbers, the chosen looping/swapping mechanism, and a pass/fail statement. If it fails, stop and report; do not add a timer-based scheduler as a workaround.

## 9. Milestones

0. **Timing spike** (section 8).
1. **Core**: domain models, synth renderer with unit tests, audio engine interface and implementation, global tempo.
2. **Metronome** screen with adjustable click and settings persistence.
3. **Sequencer** screen (8 tracks × 4–16 steps), loop playback with boundary swap.
4. **Patterns**: save, load, rename, delete, list.
5. **Polish**: persistence of last state, Linux build, Android release build, basic error handling.
6. **(Open) Playback with the screen off**: see section 12, question 1.

## 10. Testing requirements
- Unit tests for the renderer: buffer length is exactly the expected sample count for given tempo/steps (including fractional step lengths), onsets land at the expected sample indices, no samples exceed the valid range, deterministic output.
- Unit tests for model JSON round-trip and for step-count change preserving data.
- Widget tests for the main flows are nice to have.
- The timing spike measurement (section 8) is the primary acceptance test for audio.

## 11. Planned for later (do not implement now, but do not block it)
- **Arrangement/song mode**: an ordered list of pattern references with repeat counts, rendered into a longer loop or played as consecutive buffers.
- Editable voices (the parameter set already exists), per-step velocity, import of samples.
- Voice/rhythm recognition to create patterns (very low priority, possibly never).
- Possible native (Rust) audio engine behind the same `AudioEngine` interface.

## 12. Open questions and assumptions
Assumptions made in this spec, to be revisited if they feel wrong in use:
- A step is a 16th note (`stepsPerBeat = 4`), and BPM counts beats.
- The metronome models only beats per bar (no denominator).
- Default voice ladder values are placeholders.
- Tap tempo is optional.

Open questions for the owner (do not block on these; implement the simplest behavior and note it):
1. Must playback continue with the **screen off / app in background** in v1? (Needs an Android foreground service.) Default for now: not required, but design so it can be added.
2. Should the metronome sound settings be part of saved state only globally (current assumption) or ever per pattern?
